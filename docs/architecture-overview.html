Xray to Playwright migration agent

An AI agent that takes manual test cases from Jira Xray, looks at the real application, writes Playwright tests, runs them, repairs its own mistakes, and reports what passed. Every generated assertion links back to the Xray step result it checks.

The idea in three sentences

1. Problem

Hundreds of manual test cases live in Xray. Running them by hand is slow, and automating them by hand takes months.

2. Approach

Use AI only for the fuzzy work: reading plain-English steps, choosing selectors from the live page, diagnosing failures. Use ordinary code for everything that must be reliable.

3. Safety

The model never grades its own work. Fixed checks catch tests that are green but assert nothing, and block any repair that weakens an assertion.

Architecture

Code same result every run AI model decides, code checks Human sign-off

What happens at each step

StepWhoInput to outputWhat it does
Step 1: IngestCodeXray project, JQL query to ir/*.jsonSigns in with the Xray Cloud API key from .env, pulls tests through the GraphQL API, maps each one. Flags tests with no steps or no expected result instead of inventing one.
Step 2: Test case IRCodeAny source to one JSON shapeIntermediate representation: key, title, steps, test data, and expected results with ids such as ID-2-e2. Adding a new source, for example TestRail, means writing one new adapter and nothing else.
Step 3: Ground the appAILive app to app-model/<app>/Opens each page in a real browser through Playwright MCP, reads its accessibility tree, and writes page objects and a selector map from what is really on screen. Selectors never come from memory.
Step 4: GenerateAIIR + page objects to tests/<app>/*.spec.tsOne test() per test case, titled with the Jira key. At least one assertion per expected result, each tagged // @covers ID-2:ID-2-e2.
Step 5: GatesCodeSpecs to pass or failtsc catches type errors. verify checks every expected result has a tagged assertion and rejects skipped or focused tests.
Step 6: ExecuteCodeSpecs to reports/results.jsonRuns Playwright against the app. On failure it saves a screenshot, video and trace.
Step 7: Analyze and healAI + CodeFailure evidence to a small fixThe model classifies each failure (locator, timing, assertion, data, real app bug) and proposes the smallest fix, up to 3 attempts. heal-guard blocks any fix that weakens an assertion. A real app bug is reported, never hidden.
Step 8: ReportCodeResults to report.mdStatus per Jira key, the reason for each failure, and links to the evidence.
Step 9: Human reviewHumanSpecs to merged testsA person reviews the generated tests before they are merged. No automated check can prove an English sentence and its code mean the same thing.

Traceability: one id from Jira to the assertion

The expected-result id carries the Jira key, so any line in a report can be traced back to the manual step it came from.

How mistakes by the AI are caught

The dangerous failure is a test that passes but checks nothing, because re-running it never reveals the problem. So correctness is enforced by fixed checks, not by the model.

Model mistakeWhat catches it
Syntax or type errortsc --noEmit
Missing or empty assertionnpm run verify requires a tagged assertion for every expected result
Wrong or stale coverage tagverify rejects ids the IR does not define
Invented or wrong selectorThe test fails when run, then heal, then human review
Fix that weakens an assertion to go greenheal-guard blocks downgraded matchers, removed assertions and added skips
Skipped or focused test slipping throughverify fails on test.skip and test.only

Known rough edges

  • On the demo machine, npm test could not find the local Playwright command, so the agent ran the Playwright CLI directly. Same tests, different launcher; to fix in setup.
  • The browser tool hit a DNS error once while grounding. The agent used page snapshots it had already saved, and the tests then ran against the live site.
  • Only manual Xray steps and basic Gherkin are mapped. Parameterized tests, data tables and preconditions with their own steps are not handled yet.
  • Passing the gates shows each expected result is asserted, not that the assertion means what the author intended. That is why human review stays in the loop.

Next steps

  • Run a measured pilot of 30 to 50 real Xray tests: unedited pass rate (target 80%), time per test, and how often review catches something the gates passed.
  • Add a migration ledger: Xray key, spec file and status in one table, so re-runs only touch new or failed tests.
  • Open generated tests as pull requests for review, and optionally write status back to Xray.
  • Add mutation checks: deliberately break the app state and confirm the test now fails.
